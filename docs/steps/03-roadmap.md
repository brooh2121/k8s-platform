# Roadmap проекта

## Общая цель

После завершения базового bootstrap кластера проект переходит к настройке платформенных компонентов и автоматизации развертывания.

## Следующие этапы

### 1. MetalLB

Этап завершен. На нем реализованы:
- установка `MetalLB`;
- подготовка пула адресов;
- выдача внешних IP-адресов сервисам типа `LoadBalancer`.

Результат этапа: кластер готов к публикации сервисов во внешнюю сеть стенда.

### 2. ArgoCD

Этап завершен на уровне установки. Скрипт `scripts/04-install-argocd.sh` ставит `ArgoCD` и публикует `argocd-server` через `LoadBalancer`.

Цель этапа:
- хранить desired state приложений в Git;
- применять изменения в кластер через `ArgoCD`;
- перейти от ручного применения манифестов к управляемому процессу доставки.

Текущий результат: UI установлен и доступен. Преднастройка GitOps (репозиторий и Application `nginx`) выполнена на шаге 7. Связка с GitLab CI/CD еще впереди.

### 3. Ingress-контроллер

Этап завершен. Установлен `ingress-nginx`, для `ArgoCD` создан Ingress на `argocd.local`.

Цель этапа:
- маршрутизировать внешний трафик;
- публиковать сервисы по доменам или путям;
- подготовить базу для доступа к `ArgoCD`, приложениям и внутренним сервисам.

Результат этапа: сервисы можно открывать извне через Ingress-правила после записи IP в файл `hosts`.

### 4. Преднастройка ArgoCD и GitOps

Первая часть этапа завершена скриптом `scripts/07-setup-gitops.sh`:
- установлен `argocd` CLI;
- подключен репозиторий `argocd-apps` на GitHub;
- создано и один раз синхронизировано Application `nginx`;
- autosync выключен (`sync-policy none`).

Остается вторая часть этапа - связка с GitLab CI/CD:
- разобрать, где заканчивается CI (сборка и публикация артефактов) и где начинается CD через `ArgoCD`;
- при необходимости перенести или дублировать источник манифестов в GitLab.

Ожидаемый результат полной связки: изменения в Git доходят до кластера через цепочку GitLab -> `ArgoCD` -> Kubernetes.

### 5. RBAC

После GitOps и GitLab CI/CD - настройка `RBAC`.

Цель этапа:
- ограничить доступ пользователей и сервисных аккаунтов;
- разделить права по ролям;
- подготовить кластер к более безопасной эксплуатации.

Ожидаемый результат: управление доступом становится явным и контролируемым.

### 6. HashiCorp Vault

После базовой настройки доступа планируется установка `HashiCorp Vault`.

Цель этапа:
- централизованно хранить секреты;
- исключить ручное хранение секретов в манифестах;
- подготовить безопасную работу приложений с чувствительными данными.

Ожидаемый результат: появляется централизованное хранилище секретов для кластера и сервисов.

### 7. Автоматизация процесса

Этап начат. Появились `opentofu/` и ранний `terraform/`.

Уже есть:
- создание VM через провайдер Multipass;
- установка Kubernetes на ноды через OpenTofu и `scripts-tofu/install-k8s-node.sh`.

Еще нет:
- параметризации корневого модуля;
- установки `Flannel`, `MetalLB` и платформенных компонентов через IaC;
- одного пайплайна на весь стенд.

Цель этапа:
- убрать ручной запуск каждого шага по отдельности;
- обеспечить повторяемость развертывания;
- сократить время подготовки стенда;
- сделать проект более удобным для повторного использования.

Ожидаемый результат: весь процесс развертывания и настройки можно запускать как единый сценарий.

## Приоритет ближайшей работы

Ближайший практический фокус:
1. связка с GitLab CI/CD;
2. настройка `RBAC`;
3. установка `HashiCorp Vault`;
4. объединение шагов в единый пайплайн.
